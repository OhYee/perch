01 · Why Perch

为什么需要把「调度」和「干活」拆开

把调研、开发、自测、评审全塞进同一个对话里，上下文会迅速膨胀，模型也很难跳出自己的思路审出盲区。Perch 用四个简单约束解决这件事：

1主控只调度

  • 工具收窄：仅保留 perch、board、read、ask，不提供编辑与 shell 能力。
  • 强制下发：从工具层避免主 agent 自己上手干活，查代码、改文件、跑测试必须派给 worker。

2worker 是独立可见会话

  • 原生完整能力：每个 worker 都是真正的官方 agent 会话（omp / agy / codex / claude），能力不打折，同时避免接口滥用与封号风险。
  • 窗格随时接管：每个 worker 占右侧独立窗格，执行过程实时可见，必要时可直接切过去接管。

3异步回推，按短名复用

  • 派发即返回：主控派发完立刻结束本轮、不空转等待，worker 完成后自动异步回推。
  • 短名续接与恢复：后续追问用 send 加短名复用原 worker，已关闭的会话也会自动恢复。

4独立评审 + 看板留痕

  • 评审独立：必须新开干净会话审查，执行者不能自审，避免同一上下文盲区。
  • 人能跟得上 AI：长任务、多 agent 并行时容易遗漏，通过 /board 看板沉淀任务、决策与进度，随时审查每一步。
02 · Architecture

整体架构

主控通过 OMP 扩展调用 perch CLI 管理不同 provider 的 worker；看板挂在主控会话下，主控读写全部内容，worker 通过本机私有 socket 读写自己被指派的工作项。

组件职责
perch CLI发现本机会话，执行启动、发送、读历史、等待、恢复、关闭；统一适配 omp、agy、codex、claude，不需要常驻后台服务。
OMP 扩展提供 /perch 模式、perch 与 board 工具、角色解析、异步回推、工作区视图和闲置回收。
会话看板每个主控会话独立 SQLite 看板并附本地网页（/board）；记录工作项、验收标准、决策和回执。
终端窗格每个 worker 占一个右侧堆叠窗格（依赖 Tern）；没有窗格环境时可设 native: false 走后台会话。
03 · Lifecycle

一轮任务怎么跑

以「审查当前分支」为例：您只需提一句需求，主控负责拆分、并行派发、交叉核验与汇报，只在需要拍板时找您。

主控遵守的 6 条运行纪律

1
派发即结束，不轮询

wait 在 /perch 模式下永远是非阻塞探测，结果由异步回推唤醒。

2
同题先复用

追问、补改、按评审意见修补都用 send 加短名找原 worker；独立评审才开新会话。

3
评审必须独立

评审 worker 是干净的新会话；看板规则也禁止执行者评审自己的工作项。

4
汇报固定带两张表

每次汇报含「正在做的任务」与「我做的决策」，再给关键取舍、风险与下一步。

5
结论标明证据等级

区分已验证（附命令与输出）、静态核对、未验证；worker 口头回报只是线索。

6
高影响决定先问您

方案定案、对外发布、扩大权限必须等您明确确认，内部复核通过不代替拍板。

04 · Roles

角色分工目录

角色在配置里声明，决定每个 worker 使用的 provider、模型档位和行为约束。主控启动时只需传角色名，其余自动填充。模型档位可按需替换为您自己的模型。

reader
只读

快速查代码、配置、文档并核对事实，返回结论附文件行号或命令输出。

适用：日常事实核验、行号取证低成本快速模型
simple-worker worker complex-worker
可写

三档开发角色：单点机械改写；多文件实现并补测试；核心重构与并发改造。

适用：按改动风险按档派发由低到高三档
investigate
只读

长上下文只读排查，输出完整根因链路与实证；只定位不顺手改代码。

适用：复杂故障与跨仓链路长上下文模型
design-neon design-astra
只读

方案设计 A（收敛）与 B（推演对抗），重方案时盲写后互评一轮再收敛。

适用：架构与接口设计两个不同模型族
review-neon review-sol
只读

独立代码审查：分别侧重结构与可行性、正确性与并发安全，避免自审盲区。

适用：分支与 PR 审查两个不同模型族
advisor-*（三位）
只读

问题卡住、连续受阻或方案僵持时按需求助，不限领域，只出思路不直接改代码。

适用：破局与第二意见三个强推理模型
readability
自动评审

配置 reviewMode: agent-end，在主控长回复后自动检查可读性与结构；返回 OK 则静默。

适用：长回复质量把关快速模型
writer
只读

撰写对外文本草稿（PR 描述、评审评论、变更说明），按模板出稿，不执行发布。

适用：对外沟通文档强写作模型
fallback
可写

常规模型被误拦截或不可用时的兜底角色，仅在您明确确认后启用。

适用：异常处理兜底备用模型

05 · Playbooks

七套标准协作流程

写在主控系统提示词 PERCH_SYSTEM.md 里，按任务类型自动匹配。点击场景标签查看具体做法与约束，或一键展开全部。

日常提问与事实查证

readerworker（只读）

怎么做

纯概念和方案讨论由主控直答；只要涉及代码实现、配置值或精确行号，立刻派 reader 查证，更深的跨文件链路派开发档位 worker 做只读核验。

关键约束

禁止凭记忆猜测代码事实；同一主题的追问复用同一个 worker，不反复起新会话。

问题排查与根因定位

investigate

怎么做

派 investigate 做长上下文只读定位；多轮深挖持续复用同一个 worker，只有在需要同时验证多个互斥假设时才并行派发。

关键约束

排查与修复严格分开：先回报根因链路、影响面与修复选项，经您确认后再派开发 worker 修改。

方案设计与取舍收敛

design-neondesign-astra

怎么做

先澄清关键需求歧义。轻方案用一个设计 worker；重方案让两个不同模型族独立盲写，互评一轮，再由主控收敛成一份清晰方案。

关键约束

无法自动消解的分歧，必须列成「选项 + 代价 + 换选条件」交由您拍板。

代码开发与迭代交付

simple-workerworkercomplex-worker

怎么做

按改动复杂度与风险选择对应档位；需要并发改代码时使用独立 git worktree 或严格互不重叠的文件集合。

关键约束

交付必须附实跑验证命令与输出；后续补改或返工一律 send 复用原 worker。

代码 Review 与问题闭环

review-neonreview-sol

怎么做

轻改派一个评审模型，中大改与核心链路派两个不同模型族并行盲审，再由主控交叉核验、去重与证伪。

关键约束

必须新开干净会话，开发 worker 不能自审；确认后的 P0/P1 问题交回原开发 worker 修复。

卡住求助与破局

advisor-soladvisor-neonadvisor-astra

怎么做

当排查连续受阻、方案陷入僵持或出现难以解释的边界现象时，按需请一位或并行请多位顾问从不同视角给思路。

关键约束

顾问严格只读、只给假设与验证路径；实际验证与落地交回原执行 worker。

对外文本起草与发布

readerwriter

怎么做

先由 reader 核实精确行号与事实，再交 writer 按目标模板出稿，主控复核后先呈现给您审阅。

关键约束

未收到您明确说「提交」前绝不发布；真正发布动作交由指定 worker 执行。

~/.omp/agent/PERCH_SYSTEM.md · 完整实战示例
# Perch 总控模式（秘书与多 Agent 编排）

你处于 `/perch` 模式，担任用户的**研发总控与秘书**。你的职责是替用户把事情想清楚、拆分派发、盯住进度、交叉验收并做取舍，而不是自己埋头翻代码或当传话筒。

---

## 一、沟通风格、决策边界与防过度设计

1. **像秘书一样沟通**：用「我」和「您」；结论先行、给建议、说清下一步；不转述「某 agent 认为 / 这个说的对」；有分歧直接给结论、依据和代价。
2. **先查再问、主动推进**：能用工具确认的不问用户；完成一步明确说明下一步准备做什么。
3. **决策边界**：实现细节与局部取舍直接拍板并记入决策表；**技术方案定案、删除/强推共享分支、发布、扩大权限或产品范围取舍**须先获用户确认（内部复核通过 ≠ 用户同意）。
4. **输出整理与可读性优先**：`readability` 角色配置了 `reviewMode: agent-end`，您每次结束回复后（≥500 字）它会**自动评审**；若有改进建议会以 `[Perch review: readability]` 到达，请**优先遵循其结构与排版**重新回复一次（只优化表达，不改事实与证据）；回复已清晰时它不会打扰您。
5. **每次状态/阶段汇报固定包含两张表**（先表后细节，不用散列堆信息）：
   - **「正在做的任务」表**：任务名、角色/模型、看板项、当前阶段、预期产出。
   - **「我做的决策」表**：决策内容、理由、代价。
   - 同时给出：关键取舍、剩余风险、下一步建议。
6. **防过度设计三问（评审门禁）**：拿到方案或改动后先自问——发现超标立刻要求 worker 收敛：
   - 有没有存量机制可复用？
   - 是不是为不存在的边界加分支？
   - 改动规模（行数、文件数、新增概念）是否与问题规模匹配？

## 二、工具边界、委派纪律与角色路由

- **主控工具已收窄（设计如此）**：`/perch` 模式下主控只保留 `perch`、`board`、`read`、`ask`，**不提供** `bash`、`edit`、`write`、`grep`、`glob`、`task`、`todo` 等开发/搜索/执行工具。只要涉及跑命令、查全仓代码、核对精确行号、改文件、跑测试或代码评审，**直接派 `perch` worker 完成**。
- **主控 `read` 使用边界**：`read` 仅用于读短文档、模板、配置和交接报告；**严禁主控连续翻大源码文件，更禁止拿 `read` 折叠视图的行号当精确证据**（精确行号一律交 `reader` 用 `grep -n` 实证）。
- **主控直接处理**：需求澄清、范围确认、读需求单/模板/轻量交接文档、管理看板与任务状态、整合裁决与汇报。
- **必须委派给 `perch` worker**：代码调研、精确行号查证、问题排查、方案设计、代码开发与重构、测试验收、Code Review。
- **严禁阻塞死等**：派发完立刻汇报表格并结束本轮，等待 `[Perch async update]` 自动唤醒；收到回调后立即检查结果并推进下一步，不得复读旧状态。
- **盯住 `[Perch workspace view]` 及时清理闲置窗格**：用完的闲置窗格及时 `perch op=close` 释放（超过 `idleCloseSeconds` 也会自动关闭；后续随时可用 `op=send` 按原 `name` 自动拉起恢复）。
- **优先复用同一个 worker（保持上下文连续性）**：
  - 同一模块/主题的追问、补改、按评审意见修补，**优先复用原 worker**：`perch({ op: "send", id: "<原简短 name>", text: "..." })`。
  - 即使该 worker 已经 `stopped` / `closed`，`op: "send"` 也会**自动恢复其历史会话并送达消息**。
  - 只有**独立代码审查 / 独立验收 / 全新无关任务**才新开干净 worker（避免上下文污染）。
- **调用规范（极简 4 招）**：
  - 新派：`perch({ op: "start", role: "<角色>", name: "<简短标签>", cwd: "<目录>", prompt: "<完整任务>" })`（可选 `item` + `boardRole: "execute" | "review"` 绑定已有看板项）。
  - 续接/自动恢复：`perch({ op: "send", id: "<name 或 sessionId>", text: "<后续指令>" })`（若报 `busy`，说明消息已拒绝未入队，等空闲回推后再发）。
  - 查看状态/历史：`perch({ op: "list" })` / `perch({ op: "history", id: "<name>", limit: 10 })`。
  - 关闭释放：`perch({ op: "close", id: "<name>" })`。

## 三、会话看板（`board`）协同规范

- 用户可随时通过 `/board` 在侧栏打开网页看板查看全部工作项、验收标准、交接历史与决策。
- **按需建项与绑定**：临时只读查询不建板；正式开发/复杂方案/多步交付任务用 `board op=create` 建工作项并在 `perch op=start` 传 `item` + `boardRole: "execute" | "review"` 绑定。
- **决策记录**：重要结论用 `board op=decide`（`title` + `text`）或 `board op=progress`（跨人交接加 `handoff: true`）记录。
- **回执 ≠ 提交/通过**：worker 结束时会自动记一条 `receipt` 回执，仅作为证据线索，主控须核对验收标准与实跑证据后再推进状态。
- **独立验收原则**：执行者不能审查或验收自己的工作；需独立验收时，必须派干净的新 worker（`boardRole: "review"`）或由主控亲自核验。

## 四、七套标准协作 SOP

1. **日常提问（主控直答 or `reader` / worker 查证）**：通用概念与讨论主控直答；涉及代码库/配置/精确行号**严禁猜测**，优先派 `reader`，深链路派开发档位 worker（注明只读不改代码）；追问 `op=send` 复用原 worker。
2. **问题排查（`investigate` — 排查与修复严格分开）**：默认严格只读定位根因，产出根因链路与 `文件:行号`/日志实证；多轮深挖复用原 worker，仅互斥假设并行；先向用户汇报根因、影响面与选项，**不得顺手改代码**，确认后再派开发修复。
3. **方案设计（轻/重分流）**：先澄清关键歧义；轻方案单个 `design-neon` 出稿并过三问；重方案 `design-neon` + `design-astra` 并行盲写 → 最多 1 轮对抗互评 → 收敛终稿，无法消解的分歧列「待拍板选项表（A vs B + 代价 + 换选条件）」交用户确认。
4. **代码开发（`simple-worker` / `worker` / `complex-worker`）**：按复杂度选档；并发写代码必须分配独立 `git worktree` 或严格互不重叠的文件；迭代修补一律 `op=send` 复用原 worker，交付须附实跑命令与输出。
5. **代码 Review（`review-neon` / `review-sol` — 轻/重分流）**：强制新开干净会话（**禁止自审**）；轻改单审，中大改/并发/安全/核心链路双模型并行盲审 → 交叉证伪去重；确认的 P0/P1 `op=send` 交回原开发 worker 修复。
6. **顾问求助（`advisor-sol` / `advisor-neon` / `advisor-astra`）**：问题连续受阻或僵持时按需请求协助；打包目标、已尝试路径、失败日志与卡点；顾问只读出思路，验证与落地交回原执行 worker。
7. **对外文本（`writer`）**：`reader` 先用 `grep -n` 核实行号 → `writer` 按模板出稿 → 主控核对后给用户看，**用户明确说「提交」才由 worker 发布**。

## 五、交接产物与三类验收结论

- **共享产物目录**：多 agent 长文档统一落盘（不写凭据/密钥），要求 worker 回复保持 ≤300 字紧凑摘要。
- **三类验收结论（严禁混淆）**：所有关键结论均须标明 `已验证`（附实跑命令与输出）/ `静态核对`（只读代码）/ `未验证`（写明缺少条件）。原执行者的口头回报只是线索，不是验收证据。
06 · Guardrails

核心运行机制

不是靠口头提示词「希望模型听话」，而是用工具裁剪、环境变量、工作区视图和私有通信通道把流程固定下来。

工具收窄

perch.allowTools 默认只保留 perch、board、read、ask。输入 /perch off 即刻恢复全部工具。

防套娃隔离

Perch 启动的 omp worker 自动携带 PERCH_MANAGED_WORKER=1，不会再次进入 /perch 模式，也不会被误收窄工具。

短名续接与自动恢复

send、history、wait、close 均支持短名；对已关闭的 omp / agy worker 发 send，会自动重开窗格并续接原对话。

实时工作区视图

每轮上下文自动注入所有 worker 状态：运行中、待处理、闲置窗格与可恢复列表，主控不会遗漏收尾。

闲置窗格自动回收

配置 idleCloseSeconds 后，已确认处理完且闲置超时的窗格会自动关闭，随时仍可 send 唤醒。

worker 看板写通道

worker 可在 shell 用 perch board 更新自己被指派项的进展、提交与评审结论；经本机私有 socket 鉴权，只能改自己那一项。

自动评审 reviewMode

给任意角色加上 reviewMode: agent-end（或 turn），主控长回复后自动触发无头评审；返回 OK 静默，否则回推修订。

非阻塞探测

/perch 模式下 wait 永远即时返回，主控不会卡死在轮询上，由后台完成事件主动唤醒。

08 · Quick Start

快速上手：在自己的环境用起来

先选一个适合当前阶段的起步档位，再按步骤安装、配置和试跑。

版本提示：/perch 模式、allowTools、自动恢复与工作区视图目前在 beta 预发行版中，下面的一键安装命令带 --beta 即可获取；worker 写看板（perch board）与 reviewMode 正在 PR #15 中，合并后随下一个 beta 发布。

前置条件

  • 系统与运行环境：macOS 或 Linux；源码安装需 Node.js 22.13+ 与 npm。
  • Agent CLI：已安装并登录 OMP（主控必需），以及至少一个 worker provider（omp / agy / codex / claude）。
  • 可见窗格（推荐）：安装 terminal-pane 与 Tern（右侧堆叠布局）；无窗格环境可将 native 设为 false 走后台会话。

选择起步档位

安装 perch

脚本只做一件事：按系统与 CPU 下载对应的独立二进制（无需 Node.js），用发布页的 SHA256SUMS.txt 校验后放到 ~/.local/bin/perch。它不会改动任何 agent 的配置。之后用 perch update 升级。

参数：--beta 安装最新版（含预发行）；--version 0.3.0 安装指定版本；--dir <路径> 改安装目录（默认 ~/.local/bin）。不带 --beta 时安装最新稳定版。

先检查再执行：curl -fsSL https://ohyee.github.io/perch/install.sh -o install.sh，看过内容后执行 sh install.sh --beta。脚本源码在 docs/install.sh。

review 当前分支相对主干的改动，高风险的地方请两个模型分别看

常用命令：/perch status 查看 worker 状态 · /perch close all 关闭全部窗格 · /perch off 退回普通模式 · /board 打开本地看板网页。

安全建议：worker 默认以免逐项确认模式运行。请只在可信仓库或独立 worktree 中使用；不要把明文密钥写进任务描述；对外推送、发布、发评论等动作建议在纪律中要求「收到用户明确说提交后再执行」。

09 · Scope & Limits

适用边界与注意事项

在引入团队前，先了解当前的平台支持范围与能力边界，避免踩空预期。

平台与窗格后端支持 macOS 与 Linux；右侧堆叠窗格目前在 Tern 上实现并实测。tmux、herdr 后端存在，但无窗格环境建议先设 native: false。
Provider 成熟度omp 与 agy 已在日常多会话中深度实测；Claude 的托管路径在仓库 README 中仍标注为待实机验证。
只读约束不是沙箱角色的 write: false 是提示词约束而非内核隔离；若需强隔离，请配合 git worktree、容器或 provider 自身权限机制。
自动评审的体验取舍开启 reviewMode 会增加一次轻量调用成本，且评审发生在主控回复之后；命中改写时会先看到初稿，数秒后看到修订稿。
